# Reference

This chapter answers: every knob, file, environment variable, and command the plugin reacts to,
plus the quirks worth knowing. Everything here is current shipped behavior; the chapters before
it explain when and why to use these.

Paths below use `<plugin>` for the installed plugin root
(`~/.claude/plugins/cache/bitranox-skills/bitranox/<version>`). In a session you normally ask
Claude ("view my memory settings", "dream nap") rather than run these by hand - Claude resolves
the paths itself.

## Config knobs

All knobs live in one machine-local file, `~/.claude/.bitranox-memory.json`, managed via
`/bitranox:meta-memory-settings` (`settings.py view | set <key> <value> | reset`). Never
hand-edit it; the CLI validates keys and values. Every knob is a USER decision: the defaults are
the recommended state, a choice is recorded once and never re-asked, and `reset` restores all
defaults.

## Environment variables

Every variable below defaults to UNSET, which is the correct state for normal use - the plugin never
sets them for you, and a regular user never needs any of them. The hook switches
(`BITRANOX_HOOKS_OFF`, `BITRANOX_MEMORY_WRITES`, `BITRANOX_SKILL_WRITER`, `BITRANOX_MEMORY_ENGINE`,
`BITRANOX_CI_WATCH`) must be in the environment of the shell that LAUNCHES Claude Code (hook
processes inherit the session's environment; exporting inside a session's Bash command does not
reach the hooks, while a `/reload-plugins` keeps the launch environment).

| Variable                       | Default | Effect when set                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     | Who sets it, and when                                                                                                                                                                                                                        |
|--------------------------------|---------|---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|

## Command-line surface

**The memory engine** - `python3 <plugin>/hooks/memory_engine.py <subcommand>` - is the single
write path to the store. Fail-loud: success prints an explicit line; a refusal prints
`! refused: ...` and an input or usage error prints `! error: ...` on stderr, both exit 2. Only
the three check verbs exit 1, when their answer is no: `lint --tree` when it reports anything,
`topics-show` when the tree has no topic list, `topics-stale` when the level is stale.

| Subcommand                                                                                                                               | Success line                                                                 |
|------------------------------------------------------------------------------------------------------------------------------------------|------------------------------------------------------------------------------|
| `add --proj <cwd> --title T --hook H [--type feedback\|project\|reference\|user] [--body\|--body-file] [--source ..] [--pin] [--slug s]` | the fact's slug                                                              |
| `amend-pinned --proj <cwd> --slug s [--title T] [--hook H] [--body-file f] [--source ..]`                                                | the fact's slug                                                              |
| `move --slug s --from-level <dir> --to-level <dir> [--force]`                                                                            | `moved <slug>: <from> -> <to> (<direction>)`                                 |
| `relocate --slug s --from-level <dir> --to-level <dir> [--force]`                                                                        | `relocated <slug>: <from> -> <to> (...)`                                     |
| `rename --level <dir> --slug s --to-slug s2`                                                                                             | `renamed <slug> -> <slug2> at <dir>`                                         |
| `retitle --level <dir> --slug s --to-title T`                                                                                            | `retitled <slug> -> '<title>' at <dir>`                                      |
| `heal --proj <cwd>`                                                                                                                      | `healed N file(s) across M level(s)`                                         |
| `set-scope --proj <level> --scope "..."`                                                                                                 | `scope updated: <file>`                                                      |
| `topics-show --proj <dir> [--json]`                                                                                                      | `tagger: ...` and one `<topic> - <meaning>` line each; exit 1 without a list |
| `topics-set-list --proj <dir> --from-file <json>`                                                                                        | `topic list updated: N topic(s), tagger T`                                   |
| `set-topics --proj <dir> --slug s --topics a,b\|--universal\|--clear` or `--batch <jsonl>` `[--dry-run]`                                 | `set topics on N fact(s); M unchanged`                                       |
| `set-level-topics --proj <level> --topics a,b`                                                                                           | `topics updated: <level>`                                                    |
| `set-top-topics --proj <tree top> --topics a,b` (the user's decision only)                                                               | `topics updated: <tree top>`                                                 |
| `topics-stale --proj <level>`                                                                                                            | `fresh` (exit 0) or `stale: <why>` (exit 1)                                  |

| `lint --tree <dir>`                                                                                                                      | `TOTAL over-cap hooks: N \| ...`                                             |
| `tree-top --proj <dir> [--json]`                                                                                                         | `top: ...` / `store: ...`                                                    |
| `ensure-all-trees [--apply]`                                                                                                             | per-tree report (dry-run without `--apply`)                                  |

`add` upserts: the same `--slug` updates the fact in place (provenance merged, pin kept). It also
lints the hook - a warning appears when the hook exceeds the soft length cap or has no trigger
phrase ("lead with WHEN it applies"). `add` REQUIRES a hook, so it is not the way to correct a
title: `retitle` changes the pointer's link text alone, and `amend-pinned --title` is the one route
to a pinned fact's title, which `retitle` refuses by design.

Topics change only through the topic verbs. Every write of a level's descriptor (`set-scope`,
`add --scope`, and a level setup that moves a legacy `CLAUDE.md` scope block) passes one gate: it
keeps the stored `TOPICS:` line when the new text has none, and refuses a text that brings or
changes the line, an empty one included, before anything is written. A legacy block whose
`TOPICS:` line does not parse refuses `set-scope`, `add` and the level setup until that line is
fixed by hand; `ensure-memory-structure`, `heal` and `ensure-all-trees --apply` leave such a level
as it is and name it on a `! refused level, left untouched: ...` line (exit code unchanged).
`add` refuses to create a fact whose body carries a `topics:` line, and a cross-tree `relocate`
drops the line from its copy with a `~ note:`. `set-topics --batch` refuses, as an input error, a
line over 4096 bytes, more than 5000 rows, a slug named twice, a line that is not UTF-8 and a line
that is not a row object.
`set-topics --clear` works on a pinned fact; tagging one is refused. `set-topics --dry-run` also
runs under `BITRANOX_MEMORY_WRITES=off`. A `--topics` value that is no topic list is a usage
error. A level reached through a symlink is named by its own path below the tree top. `add`,
`set-scope`, `move` and `relocate` refuse a level whose path crosses a directory every walk over
the tree's levels prunes (`.git`, `node_modules`, `target`, a virtualenv such as `.venv-3.12`,
the store, ...): one name rule, `uuid_store.is_non_level_dirname`, shared by every such walk.

A fact bound to a topic, with `title:` and `description:` in its body and no line pinned, is
placed by topic: `render-topics` gives it one line at each level that has one of its topics
while no level above it does, and one at the tree top when none does. `--scope tree` renders
every level; `--scope chain` only the levels from `--proj` up to the tree top, adding no line
below a level that holds it and dropping such a lower copy. `--dry-run` writes nothing and takes
no lock. One level's block may hold at most 1 MiB of lines; a render, `add`, `amend-pinned`,
`retitle`, `rename`, `move` or `relocate` that would leave a block past it AND larger than it is
now is refused before writing and names the route that frees the bytes, so a write that does
not grow an over-full block still goes through. Such a
fact is refused by `move`, `relocate` and `add --pin`, and by `add` from a level holding no line
of it; `rename` and `retitle` change every line of it. `set-topics` refuses to bind a fact whose
line cannot be rendered yet (no `title:` or `description:`, a line that differs from its body, a
legacy `uuid:` pointer), naming the repair; un-binding collapses its lines to one at the tree
top. The full contract is in `meta-self-improve`'s `references/memory-backend.md`.

**Consistency audit**:
`python3 <plugin>/skills/meta-self-improve/reconcile_memory_index.py --check <dirs...>` (a level
dir or an altitude chain) - must end `TOTAL problems: 0`; consolidations verify with it. It also
reports a `repeated line` (a fact placed by topic held at a level and again above it), which
`render-topics --scope chain` drops. `--check-tree <anchor>` runs the same audit tree-wide and
must end `TOTAL tree problems: 0`; for facts placed by topic it reports `render drift` (lines
missing, differing from the body, or placed elsewhere, repaired by `render-topics --scope tree`)
and `the placement by topic could not be checked` when the render would refuse. `--archive <slug>
<level>` forgets a fact; for one placed by topic it drops the other levels' lines, then moves
the body and drops the line at `<level>` (a failed write there moves the body back).

**Dream scheduling**: `python3 <plugin>/skills/meta-dream-tree/dream_state.py due|mode [cwd]` -
query whether a consolidation is due, or print the effective dream mode; `dream_state.py done
[cwd] --kind nap|tree [--dream ID] [--jev-skip SITE=REASON]` marks one done (a tree dream only
once each of its Jev shadow sites has rows for that id or a skip reason). `dream_state.py
nap-decline [cwd] --by user` records that the user declined an owed post-compaction nap: the Stop
gate stops blocking on it until the next compaction owes a new one, while the obligation itself
stays until `done`.

**Generated artifacts** (contributors): `python3 <plugin>/hooks/build_skill_triggers.py` rebuilds
the router map, `python3 <plugin>/hooks/build_skill_docs.py` rebuilds the
[skill catalog](skills.md); both support `--check` and are enforced by pytest sync tests.

## Model-callable tools

A hooks module (`hooks/mods/register.ts`, listed under `"modules"` in `hooks.json`) gives the model
five tools, each relayed to `hooks/mod_bridge.py`, which answers with one JSON envelope. A refusal
comes back as an ordinary result with `ok: false`, the kind and the reason, and nothing written. A
call that could not run at all (the bridge failed, timed out or answered with exit code 2) reaches
the model as a tool error instead.

| Tool                           | Effect                                                                            | Refuses                                                                                                                                                                                                                                                                                                             |
|--------------------------------|-----------------------------------------------------------------------------------|---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `mcp__bitranox__backlog_list`  | Lists the items of the repo's `OPEN-WORK.md` (open by default) as data            | A `state` other than open, closed or all, and a directory outside a repository; a missing file returns an empty list with a note                                                                                                                                                                                    |
| `mcp__bitranox__backlog_add`   | Adds one item (rank, origin, text, size, open, next), creating the file if absent | A directory outside a repository, a rank that is not 1 to 999999 or that any line already uses (closed included), a bad origin or date, an empty field, a field with a line break, a tab or another control character, text a UTF-8 file cannot hold, or a field that contains a ` \| size: ` style label separator |
| `mcp__bitranox__backlog_close` | Closes one solved item by rank by DELETING its line; returns the line and reason  | A directory outside a repository, an unknown rank, an already closed item, a rank that labels several open lines, and an empty or multi-line reason                                                                                                                                                                 |
| `mcp__bitranox__memory_add`    | Writes or updates one curated memory fact at a level (default: the session cwd)   | A level that is not a directory, a bad type, an over-long hook, an empty body, a new fact whose body brings a `topics:` line, a level whose legacy `CLAUDE.md` scope block has a `TOPICS:` line that does not parse, a bad or colliding slug, a pinned entry, an excluded level                                     |
| `mcp__bitranox__contrib_add`   | Queues a contribution (what, target, why) for the next dream                      | An empty or multi-line `what`, `target` or `why`; a duplicate or already-shipped entry is not a refusal but returns `queued: false` with the reason                                                                                                                                                                 |

`memory_add` writes like the CLI's `--proj`: a `level` with no memory store yet creates a new tree
top there, and a level without a pointer block is scaffolded.

| Requirement          | Detail                                                                                                                                                |
|----------------------|-------------------------------------------------------------------------------------------------------------------------------------------------------|
| Claude Code 2.1.259+ | 2.1.242 to 2.1.258 log a load error for the module and skip the tools; older builds ignore the `modules` key. Every classic hook works on all of them |
| Windows with WSL     | Point `CLAUDE_CODE_GIT_BASH_PATH` at Git Bash so a bare `bash` does not resolve to the WSL one                                                        |

## Quirks

- **Update vs reload**: `/plugin marketplace update` serves NEW sessions; a running session keeps
  its version until `/reload-plugins`. Details in [installation.md](installation.md).
- **Windows without Git Bash**: hooks are skipped silently (never an error); skills still work
  when invoked. Details in [installation.md](installation.md).
- **Guards judge the command they see**: a PreToolUse guard evaluates repo state when a command
  is submitted. A compound command that prepares state AND commits in one line is judged on the
  pre-command state - run the preparation as its own command first.
- **Skill authoring is gated twice**: `SKILL.md` writes need a fresh skill-writer receipt (issued
  by `bitranox:meta-skill-writer`, 8-hour TTL) AND that skill loaded by the editing agent itself, so
  a subagent cannot edit on its parent's receipt; `BITRANOX_SKILL_WRITER=1` set at launch bypasses
  both. In this repo the repo gate additionally requires the committed checklist artifacts. See
  [CONTRIBUTING.md](../CONTRIBUTING.md).
- **Description changes regenerate two artifacts**: the router map and the skill catalog are
  derived from skill descriptions; sync tests fail the suite until both are rebuilt.
- **Recall noise filtering is learned per project**: a word judged conversational filler in one
  project never suppresses recall in another.
