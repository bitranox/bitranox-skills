# compuse-toolbox: when each tool applies

The full entry for every row of the Tools table in `../SKILL.md`. Each entry completes the
sentence "Use it when you would otherwise hand-roll...": what the tool replaces, the traps the
hand-rolled version falls into, and what the tool reports. The table carries a one-line
summary and the launch command; read the entry here before relying on a tool's verdict.

## `procsig`

`pgrep -f` / `pkill -f` - which self-matches the shell running it and can kill your own session; with `--peer`, `ss -tnp | grep HOST:` plus a `ps -o ppid=` walk to learn which process, and which Claude session, holds a connection to a shared host or port

## `suite_busy`

`pgrep -f pytest` or `ps aux | grep pytest` to decide whether a test suite is already running before you start a gate - which matches the shell running the check, matches `mypytestish` and any `bash -c` string that mentions the word, and looks in ONE directory while every git worktree is a checkout with a suite of its own. It examines the repo's main checkout AND every worktree, attributes a process by its `/proc/<pid>/cwd` to the deepest checkout holding it, matches by argv TOKEN (pytest, `-m pytest`, a bmk or make gate verb, plus your own `--match "cargo test"`), and excludes itself and every ancestor, so neither it nor the shell that ran it is ever reported; a `bash -c '... pytest ...'` string is one token and never matches, while the suite that shell starts is its own process and is found. It reports how many processes and checkouts it examined, how many of its own chain it set aside (`processes_excluded`) and how many it could not read (another user's cwd, counted in `skipped`). It refuses (exit 2) only when not one cwd could be read, its own chain included: on a CI runner whose only readable processes are its own chain, the answer is FREE (exit 0), not a refusal. Linux only: without /proc it says so and exits 2

## `git_state`

a `git rev-parse` + `git status` branch/sync/dirty check before a risky commit or bulk op (`--fetch` first, else the counts are as of the last fetch; an upstream of another name, `feat` tracking `origin/master`, is flagged and judged against `origin/feat`); or "which copies of this file across a tree are tracked-and-modified, gitignored, untracked, or outside any repo?"

## `conflict_scan`

a `grep -rn '^<<<<<<<'` sweep for merge-conflict markers, one `path:line: text` row per marker (exit 0 clean / 1 markers / 2 a path or directory could not be read; a dangling or looping symlink is skipped with a stderr note, not an error; a symlinked directory met inside a walked tree is not followed and is named on stderr); a lone ======= outside a <<<<<<< ... >>>>>>> span is skipped only as a heading rule - a setext underline (text above, a blank line or end of file below) or a whole RST overline/title/underline block - and with text on both sides it still counts

## `quotecheck`

a subagent's quote-back taken on trust, or a one-off substring check of it - splits a quote at the joiners agents use, normalises it and looks it up in the cited dir, one verdict per quote (OK / MISMATCH / NONE / TOO-SHORT; exit 0 / 1 / 2), also over a Workflow journal

## `raisesmatch`

reading a `pytest.raises` or `pytest.warns` `match=` by eye to decide whether it pins the refusal or whether any unrelated refusal would pass it (vacuous patterns are flagged per call site)

## `conflict_resolve`

**you are resolving a merge conflict hunk by hunk** - keep ours or theirs, keep both sides of a CHANGELOG conflict with the newer entry on top, or take the diff3 base - with a hand-written `re.sub` over the markers and a write-back, which under DOTALL spans two hunks, keeps a diff3 base section as if it were ours, misses CRLF lines and never checks the hunk count. One rule per hunk (`--hunk N=RULE`, `--match REGEX=RULE`, `--all RULE`; RULE is `ours`, `theirs`, `base`, `both`, `both-theirs-first`, `ours-minus-theirs-deletions` or `file:<path>`; `ours-minus-theirs-deletions` is the diff3 hunk where upstream deleted or moved away a line next to one your side added: it keeps ours and removes only the base lines theirs deleted, and refuses when theirs did anything but delete; `ours` is the `<<<<<<<` side and `theirs` the `>>>>>>>` side, so in a rebase `theirs` is the commit being replayed, and `both` puts ours first); it refuses with exit 2 and writes nothing on a wrong `--expect-hunks`, a hunk with no rule or two, a `--match` hitting no hunk or several, `base` or `ours-minus-theirs-deletions` on a hunk with no base section, and malformed or half-resolved markers. Line endings and a missing final newline are kept, the write is atomic, and the result is re-scanned: exit 1 if a marker remains. `--list` shows each hunk and writes nothing. In a Markdown file (`.md`, `.markdown`, `.mdx`) a join where an ATX heading meets a non-blank line gets a blank line between them, so a `both-theirs-first` CHANGELOG join does not glue one entry's heading onto the other's last bullet

## `ci_wait`

waiting for GitHub Actions to finish on a commit you just pushed - every workflow that fired for it, not whichever shows up first - before tagging a release. Name the commit with `--ref HEAD` (or `origin/master`, a tag): the tool resolves it with `git rev-parse --verify` in the `--repo` directory when one is given (a linked worktree's HEAD is not the main checkout's), else (no `--repo`, or an `OWNER/NAME` one) in the current repo, and prints the sha it resolved to (the same value `--json` reports as `data.sha`), so you never type or complete one - a sha padded from a short display passes every format check and matches no run, and `--ref` also works where your own `$(git rev-parse ...)` is refused, as in a worktree-isolated session. Run it from inside the pushed repo, or pass that checkout as `--repo DIR`: a name that is not a commit there, or a cwd outside any repo, exits 2 before any poll, and so does `--ref` with an `OWNER/NAME` `--repo` from a cwd whose git remotes all name a repository other than that `--repo` (its sha would be polled where it was never built and end `no-runs`). After `gh run rerun` the run keeps its id and sha and the listing can still show the old attempt green, so pass `--min-attempt <old attempt + 1>` (`gh run view <id> --json attempt` reads the old one): without it the wait returns that stale success on its first poll while the new attempt is still running. `--sha` stays for a sha from outside (a CI URL); exactly one of the two is required. Refuses a sha that is not the full 40 characters, because a short one silently matches nothing and the poll loop then spins to its deadline looking busy; an empty match is a verdict, not a keep-waiting: it is reported as `no-runs` (exit 2) once the grace period (`--appear-grace`, in seconds, default 120, counted from the first poll that found nothing) runs out, which is what gives a just-pushed commit time to have runs at all. A FAILING `gh` gets a grace budget of its own instead of ending the wait, because an HTTP 502 from the API is weather and not a verdict; a sustained outage still ends it, reported as `error` (exit 2) with gh's message rather than as a timeout. A spent API rate limit is not weather: after each failed call the tool reads `gh api rate_limit` (free), and when its core remaining is 0 the wait ends at once as `rate-limited`, exit 2, naming the reset time in local time and UTC, because the limit is shared by every session on the account; a quota it cannot read, or one with requests left (a secondary limit's 403), keeps the retry. An all-green answer is CONFIRMED after a short settle (`--settle`, 20s) before it is returned, because the runs for one push are not created at the same instant, so an early all-terminal poll can be a partial set read as the whole one; a failure is reported at once, since a later run cannot rescue it. The settle BOUNDS that window rather than closing it: a run created after the confirmation is outside what any wait can see, so raise `--settle` on a repo whose workflows register slowly. A green seen so close to the deadline that the settle was cut short, or never re-polled at all, is still reported as success, with the summary saying so. Runs are asked for by sha on the server, so an older run of that sha is never outside the `--limit` window; every `gh` call is bounded by a timeout and `--timeout` is a wall-clock deadline; an `--interval` below 5 seconds is refused (exit 2), because every poll is one API request and the deadline keeps polling for the whole wait; a run that concluded `skipped` does not fail a push, but a push where every run was skipped is reported as failed (nothing ran). `--repo` is optional and falls back to the current directory's repo, resolved once before the first poll. With no `--event` every run on the sha counts except a scheduled one (a nightly run GitHub queues on the same head sha would otherwise hold the verdict open or fail it), so a fork pull request's `pull_request` runs are seen; `--event push` counts only push runs and `--event any` counts scheduled runs too. A fork-PR run awaiting approval (`action_required`) is reported at once as `pending-approval`, exit 2. A run left `queued` for `--queued-grace` seconds (default 900, 0 disables) with none of its JOBS yet started (one job awaiting a runner keeps a run `queued`) and no other run going is `stuck-queued`, exit 2, naming the run id (a likely duplicate if its workflow already succeeded on this sha); cancels nothing. A failure where GitHub refused to start EVERY failed run for billing (zero steps, a payments annotation) is `billing-blocked`, exit 2: no wait or retry fixes it. `--json` prints {ok, command, data: {state, summary, runs, sha, jobs}, skipped} (`jobs` only on `failed`), `sha` being the commit watched (absent when the sha itself was refused, and then `error` says why). The default `--timeout` is 3600 s, and a timeout (exit 2) names each workflow's usual duration (the median of its last successful runs) so the next deadline can be sized; a deadline reached while `gh` was failing is reported as a timeout that counts the failed calls. `--workflow NAME` waits on that workflow's runs only. Each poll names per-job progress (`15/16 jobs done, 0 running, 1 queued (<job> queued 2m00s)`), a run that reads green while a job is still unfinished is not counted green, and a job already concluded `failure` is named at once; `--fail-on-failed-job` exits 1 on it without waiting for the run to end. A poll line names only the jobs failed BY THAT POLL, so never quote one as the push's failed cells: a `failed` wait (exit 1, `--fail-on-failed-job` included) reads every job of every run once more and, in text mode, prints them on stderr just above the verdict line, failed ones (`failure` or `timed_out`) first (`jobs of run <id> (<workflow>, <run conclusion, or status if unfinished>): 2 of 16 failed`, then one `<conclusion>  <job>` line each, a job not finished yet showing its status instead); `--json` carries them as `data.jobs`, one `{databaseId, workflowName, state, jobs: [{name, status, conclusion}]}` per run, `jobs` null when they could not be read. The verdict line stays last and unchanged. `--repo` takes `OWNER/NAME` or a local checkout directory. A `no-runs` verdict names its two live causes: the sha is on no remote-tracking branch, or no workflow trigger matches the pushed branch

## `ci_triage`

piping a build/CI log through `grep`/`sed`/`awk` to find the error lines

## `pushcheck`

**you are about to push and want to know whether this repo is even public, and whether the push PUBLISHES something private** - a local path, an internal hostname, an operator's username or an RFC1918 address. It answers BOTH halves: visibility comes from the REMOTE, never the directory name, because a tree that files repos under `public/` and `private/` folders is a convention that drifts - measured, a folder named `public/...` held a private repo, and a name-based guess is also wrong the other way, calling a public repo private and waving the scan through. Scans the ADDED lines of EVERY commit in the range rather than the endpoint diff (a leak added and then removed inside the range is still published), so a commit that REMOVES a leak stays pushable - and every commit MESSAGE, which the push publishes too: on a public repo a finding in a message refuses even a removal-only range. A binary file's content is never scanned, so each one is NAMED instead (the JSON `skipped` list, a `not scanned` line), and a range that adds only binary content is refused, never called clean. Every non-answer fails closed: unknown visibility, an unreadable range and an EMPTY range are refusals, and the report always states how many lines it read, because "no findings" after examining nothing is indistinguishable from a clean result. Documentation-safe values (RFC5737 ranges, `example.com`, loopback, `/home/user/`, Tailscale's resolver `100.100.100.100`) are deliberately not findings; pass your own infrastructure names with `--denylist-file`, which is never shipped and is the only check that catches a bare dotless internal hostname (the built-in host rule needs a dot). It is read in `redaction_scan`'s list format, so one list serves both jigs unchanged: one term per line; a blank line, and a line whose first non-blank character is `#`, is a comment; a `term==>replacement` rule searches for the term before the first `==>` and ignores the replacement; every term is stripped of surrounding whitespace and found as a case-insensitive substring by casefold (`Strasse` also finds the sharp-s spelling); a file that is not UTF-8 text, or that yields zero terms, is refused with exit 2 rather than read as clean. Exclude a security fixture's own sample values with `--exclude` (a project that TESTS for private-looking strings necessarily contains them, and an exclusion that matches nothing is reported rather than silently ignored)

## `redaction_scan`

`git diff | grep -iFf <private names list>` before publishing - where a bare `#` comment line matches every `#` in the diff, a `name==>replacement` rule is searched whole and never finds the name, and a removed or context line reads as a leak. It parses the list (blank and `#` lines are comments, the pattern is the text before `==>`), matches case-insensitive literal substrings in ADDED lines only (`--range` reads every commit and its message, `--staged` the index, `--worktree` tracked changes plus untracked files), and first plants an added line per pattern that must hit, refusing if one does not. `--redact-hits` names a hit's rule by index, list line and hash, never by its text. An added line that only re-spaces a line the same file section removes (a table formatter re-padding rows nobody edited) is reported apart as re-padded and does not make the scan exit 1; a changed cell is still a hit

## `backstop`

**you kicked off a background agent or a long job and do not want to sit watching it** - what shouts at you if it hangs and never comes back, but stays quiet if it finished. Arms a deadline that alerts ONLY on non-completion, and REFUSES to arm when its exit signal is ALREADY true - the trap that makes a hand-rolled waiter report success on its first poll while covering nothing. Watches the last artifact the worker writes, a git HEAD moving off a base, or a sentinel. A done-file counts as finished only once it is NON-EMPTY and its size has HELD for one poll, so a worker that touches its report early and appends cannot make the backstop stand down mid-write. Refuses (exit 2) a non-finite or non-positive `--deadline`/`--interval`, a `--base` that is not a 7+ hex sha, and a `--repo` that is not the repository root (a subdirectory, or a nested checkout whose `.git` is gone, would read the parent's HEAD); a `--repo` that vanishes mid-run exits 2 (signal LOST), never a TIMEOUT

## `markerwatch`

waiting for a log line that says a run finished with `tail -F LOG | grep MARKER` or a `grep -q` loop - which a start banner, the waiter's own echoed command, a quoted marker or a case-folded neighbour (`FAIL` inside `FailureReason`) answers early. A marker is a LITERAL, case-sensitive line PREFIX (after an optional `--strip-timestamp`); `-i` is refused, and so is a blank, indented, `^`-led, `.*`-holding or punctuation-only marker (`====` is decoration every banner shares). `watch` follows the log like `tail -F` (waits for it to appear, reopens it after truncation or rotation), prints `--marker` and `--terminal` lines, and exits 0 on the first `--terminal` line, 1 at `--timeout` (default 3600 s); `--from start|end` is required, because only you know whether the log already holds an OLD run's marker. `calibrate FINISHED_LOG` (or `watch --calibrate`) refuses a terminal marker that matches a known-finished run zero times or more than once

## `enforced`

**a config setting is supposed to restrict something - does any code actually DECIDE on it, or is it only declared, parsed and read?** Classifies every mention: DECISION (compared to, or branched on) and CLAMP (a min/max cap) ENFORCE; declaration, config-file, plain reference, test, docstring and comment do not - so both-empty IS the answer rather than a hit count that cannot tell a reader from an enforcer. Catches the field that is typed, schema-validated and bounds nothing, which reads as safety because it is loud when malformed and mute when ignored. Whole-name AST matching, and it follows one alias hop. Exit 0 enforced, 1 parsed but never enforced, 2 not found or incomplete (an unreadable file or directory and no decision elsewhere)

## `confound`

**you changed a few things between runs, one number came out different, and you want to write down WHICH change caused it - can that table actually say?** Reports which pairwise comparisons may carry a causal claim and which are CONFOUNDED because more than one thing moved. `--claim disk` answers the sentence you were about to write and NAMES what else moved. Two rules easy to miss by eye: a setting recorded on one run and ABSENT on the other DIFFERS, and an isolated setting whose outcome did NOT move supports nothing - two identical runs have no difference for anything to have caused. What it does NOT infer for you: a CONFOUNDED pair whose outcome did NOT move owes no attribution and still supports a NULL reading - neither dimension had a detectable effect at that scale, barring exact cancellation - never a cause. A control pair that varies ONLY the nuisance dimension and agrees exactly shows that dimension is inert, which is what licenses reading the confounded pair. State either inference in the write-up yourself rather than letting the CONFOUNDED verdict stand alone. It sees only confounds among the things you thought to RECORD, so it is a floor and never a proof. Every --arm starts with a LABEL; a missing label, a key given twice, an outcome on some arms but not all, and outcomes in different units under --outcome-tolerance are refused (exit 2). Exit 0 = the claim is supported (no --claim: nothing confounded), 1 = refuted or a confounded/unexplained pair, 2 = refused input, a crash, or INCONCLUSIVE (the claim is isolated but the outcome moved less than --outcome-tolerance; --json `data.inconclusive` names the pairs)

## `transcript_index`

**something you worked out in an old session but never wrote down** - full-text search across EVERY past Claude Code transcript at once, rather than opening them one at a time. Indexes narrated prose only: tool calls and their output are NOT indexed, so a miss means it was never said in words, not that it never happened

## `jsonl_grep`

a `json.loads` loop to filter a JSONL by type/role or extract a field - or a hand-rolled walk over a whole CORPUS of transcripts to learn what values a field really takes

## `transcript_tail`

parsing a Claude Code transcript JSONL - for the last user/assistant text, or for the WHOLE session: every text turn, or every call of one named tool with its input, each carrying the JSONL line it came from. To mine a subagent's JSON result read assistant records only (`--role assistant`): the brief you sent it holds the same keys and matches first

## `claim_check`

a `grep -c` / `grep -l` sweep to decide whether some text is already present in a set of files. `--literal` matches the text as written instead of as a regex, ignoring backticks, `*`, `_` and runs of whitespace, so a phrase quoted from rendered Markdown still finds its marked-up source

## `grep_all`

a repo-wide `grep -r` that must be COMPLETE - it silently skips gitignored files

## `gate`

running gates then acting on the result - `<gate> | grep summary && git push`. Also the three ways a CORRECT exit status still proves nothing: a shared default log two concurrent runs both append to, a filter that matched ZERO tests, which exits 0 and reads as a pass, and - when it runs in the BACKGROUND - a completion notification that reports THIS runner's status rather than the gate's, so read the verdict from gate.py's own STDOUT (the background task's output): the `[PASS]`/`[FAIL] <cmd> (rc=N)` lines and the closing `ALL GATES PASSED` or `GATE RED - follow-up NOT run` are printed THERE first and then appended to `--log` after the gate commands' output and their `=== gate: <name> :: <argv> ===` headers, so a watcher polling the log sees the same lines. Each run in the log opens with `##### gate run <time> #####`, then `cwd: <dir>` and `repo: <work tree top level>`, which is what tells apart the logs of several sessions gating the same command; a pinned `--log` reused across runs holds several verdicts, so read the LAST one. Give any watcher a second exit that fires when the gate process ended with NO verdict line in the task output: a worker that died writes no verdict at all, and must not read as a slow one. The exact stdout shapes: each verdict line is INDENTED by exactly two spaces, `  [PASS] <cmd> (rc=0)` or `  [FAIL] <cmd> (rc=N)`; a `--summary` match below it is indented further (nine spaces); the closing line is UNINDENTED and exactly `ALL GATES PASSED` or `GATE RED - follow-up NOT run` (with or without `--then`), followed by `log: <path>`. So `^\[PASS\]` and `^\[` match NOTHING on a passing gate and read as no verdict; match verdicts plus the closing line with `grep -E '^  \[(PASS|FAIL)\] |^(ALL GATES PASSED|GATE RED - follow-up NOT run)$' out.txt` (the two-space anchor also skips a `--summary` line that echoes `[PASS]`). A `--gate` runs WITHOUT a shell, so it holds ONE command: a bare (unquoted, unescaped) `&&`, `||`, `|` or `;` inside it is refused (exit 2) rather than handed to the program as an argument, and so are stray words of an UNQUOTED multi-word gate that land beside `--gate` - quote the whole command

## `winlog`

`iconv`/`strings -e l` on a WINDOWS log whose text `grep` cannot find, or that `cat`s with spaces between the letters - UTF-16, BOM, or MIXED encodings

## `transfer`

a `curl --limit-rate` / `rsync --bwlimit` big-file download or host-to-host copy that must respect a REAL speed limit (the units differ per tool: `curl 8M` is 8 MiB/s = 67 Mbit, `rsync --bwlimit` is KiB/s), or judging whether a long job has hung

## `fleet_ssh`

an `ssh -i <key> -o BatchMode=yes -o ConnectTimeout=N` one-liner retyped per call, or an scp whose login user has to go INSIDE the path (`root@host:/p`) and gets forgotten

## `winpytest`

copying a repo to a Windows test host and running its pytest suite there over ssh - where cmd.exe, not a POSIX shell, runs the remote side: `if exist X rmdir /s /q X & mkdir X` runs the mkdir only when X EXISTED, a forward-slash scp destination fails with `dest open ... Failure`, and PowerShell syntax fails outright. It ships `git archive HEAD` (naming uncommitted changes as NOT shipped), clears and creates the destination in separate ssh calls, scps to a backslash path, and runs `uv run [--frozen] [--extra X] pytest ARGS` with `--env KEY=VALUE` set first; the destination is deleted before each run, so it must be an absolute path at least two levels deep. Exit 0 passed / 1 tests failed / 2 no verdict (a step failed, pytest exited 2-5, or rc 1 with no tally or short summary, i.e. pytest never ran)

## `diffbehave`

a loop that runs an OLD and a NEW version of a script (or two CLIs meant to be equivalent) on the same inputs and diffs stdout/stderr/exit code by eye - or proving a hand-rolled detector is not a rubber stamp that always says SAME. A side that did not run at all (not found, exit 126/127, a missing script operand) is ERROR, exit 2, never DIFFER, so a typo cannot satisfy `--expect-differ`. To compare a module at a git rev with the working tree: `git show REV:path/m.py > m_rev.py`, then one driver that imports a module by path and calls the function on argv[2]: `--a "python3 driver.py m_rev.py" --b "python3 driver.py path/m.py" --case-file cases.jsonl` with each case's `args` naming an input

## `adjudicate`

confirming a claim about a guard - or trusting a hand-rolled detector or scan written during a review - by running the ONE input that shows it. A guard that fires on your probe, or a detector that finds nothing on the real tree, has told you nothing until you know it does NOT fire on an input differing only in the thing claimed - without that second run, "it fired" and "it fires on everything" are the same observation. Runs the subject on a probe AND a control and scores the pair in THREE buckets: CONFIRMED (probe fired, control did not), REFUTED (probe did not fire), UNUSABLE (both fired - the control did not discriminate, so nothing was measured). UNUSABLE is the one that gets lost: folded into REFUTED it reads as a clean sweep over broken controls, so any UNUSABLE claim makes the whole run exit 2 (could not answer) and the report cannot be mistaken for all-clear. PATH MODE is for the detector or scan: it runs the subject on a PLANTED path (one you seeded with the thing it hunts) and a CLEAN path instead of stdin, and refuses a missing path or the same place on both sides before anything runs (exit 2, a usage error), so a typo is never scored as fired

## `newest`

"which backup/log/snapshot is the latest?" answered with `ls <glob> | sort | tail -1` - a longer name sharing the same date prefix sorts AFTER a shorter, newer one, so it silently picks the wrong file OR directory; ALSO when a later pass (compression, re-encoding, a fixup job) rewrote the files, because mtime then records THAT pass and not the content - the default run warns when the two keys disagree about the answer; under `--name-timestamp` the reported age comes from the stamp too (a stamp ending in `Z` is UTC, an unzoned one local time), and a stamped path that no longer exists is skipped, never picked

## `redcheck`

reading by hand every notes/rules file a machine feeds an agent at startup, to answer "does the agent ALREADY know this, so my baseline/RED prompt cannot really fail?" - it assembles that startup context itself (the `CLAUDE.md` + `CLAUDE.local.md` chain and memory bodies, gitignored ones included) and names the file that already teaches your scenario; also flags a scenario that hands over its own answer (ships in `process-test-driven-development`, not here)

## `wtclean`

`du | sort -rh` then `rm -rf` hunting for the disk space a DELETED worktree never gave back - `git worktree remove` drops the checkout and leaves its per-topic build cache sitting outside it, gigabytes each, listed by nothing (ships in `git-worktrees`, not here)

## `claudemd_variance`

"which `## ` sections are duplicated across my CLAUDE.md files, and where should they live?" - hand-splitting, hashing and grouping them, then guessing the common ancestor instead of computing it (ships in `meta-consolidate-claude-md`, not here)

## `srccount`

"how big is this codebase - how many source files do we actually own?" answered with `find DIR -name '*.py' -not -path '*/.venv/*' | wc -l`. That exclusion list IS the instrument: vendored trees outnumber first-party source by one to two orders of magnitude, so whatever it misses (`venv-*/`, `site-packages/`, a checked-in upstream tree) DOMINATES the answer instead of nudging it, and the command still exits 0 with a confident wrong number. Excludes on EVIDENCE, not just names - a dir holding `pyvenv.cfg` or `CACHEDIR.TAG` is a venv or a build cache whatever it is called - always reports the excluded share, and always breaks the count down per extension AND per directory so a dominant subtree or a wrong `--ext` cannot be quoted by mistake. A directory it cannot read is "could not count" (exit 2, listed as skipped), never a smaller number - unless it sits inside an excluded tree, where only the excluded count becomes a floor (a stderr warning, the exit unchanged). `--audit` asks the other question: is that skip list still right for THIS tree

## `mem_levels`

"which curated memory levels exist, what sits at each, and which level holds this fact?" answered by walking every `CLAUDE.local.md` with a hand-rolled `mem:` regex - a `[a-z0-9-]+` class does not merely truncate a DOTTED slug, it fails to match the line at all, so the pointer goes invisible and its body reads as an orphan

## `anchor_edit`

a Python one-liner that edits a file by `str.replace`, `partition`, or a span computed between two markers, in a SCRIPT or across many files - the interactive Edit tool already refuses a non-unique anchor, these do not. All three have success-shaped no-match branches, so a missed anchor writes a file that looks edited and is not, or edits the wrong one entirely. Refuses an absent or ambiguous anchor, makes a span state how many lines it removes and what must survive, splices the new text verbatim, and backs up (byte-exact) a file git could not restore - uncommitted, skip-worktree and assume-unchanged work included. Keeps CRLF line endings; exit 2 = refused with nothing written (--json marks it `data.refused`) or a usage/IO error - there is no 1. `batch --spec FILE` applies many exact replacements across files, every count (default 1) checked before ANY write, with an optional per-file `expect_line_delta`. Inside a git work tree the backup goes under the git dir (`<git-dir>/anchor_edit-backups/...`), never beside the file, so no `git add` can stage it. `insert` takes `--after|--before` and **`--after` is the DEFAULT**, so an omitted direction lands the text AFTER the anchor: to PRECEDE a block, anchor on its opening line and pass `--before`. Every path is ABSOLUTE: each subcommand's `F` (`replace`, `insert`, `replace-span`, `reap`) and each `file` in a `batch --spec` is refused when relative (exit 2), since a sibling repo holding the same template-copied text is where the anchor would match the wrong file

## `mutation_arm`

"does this test actually assert anything?" - proving a test is not vacuous by breaking the code and requiring it to go red. Hand-rolling the arm is where it goes wrong: the verdict gets read off a grep of the log, where a `pytest.raises(X)` SOURCE line echoed in the traceback makes X look raised while the summary says DID NOT RAISE; the arm fails on an EARLIER assertion and reads as the one you meant; and a single mutation is absorbed by layered validation, so a covered line reads as uncovered. Mutates by exact anchor (several at once, as ONE arm), runs the named test, reports the failing ASSERTION from pytest's summary, and restores from a copy taken first - never `git checkout --`, which discards uncommitted work. `--timeout` bounds the arm, because a mutation can make a test SPIN rather than fail when the test's only exit is the behaviour being mutated: unbounded, one such arm hangs the whole battery and reports nothing. A timeout is its own verdict, never `killed`, and the restore still runs when it fires - the copy is taken before the first edit and put back in a `finally`. A kill from outside restores too: SIGTERM, SIGHUP and SIGINT (SIGBREAK on Windows) stop the arm's process tree, restore every source, and exit 128 + the signal number (143 for SIGTERM, 130 for Ctrl-C) with a stderr line saying whether every source is back; a battery then runs no further arm and no final baseline and prints no report (no envelope under `--json`), so a finished arm's runner output survives only in its `--log-dir` log, when one was given. For a SIGKILL, which nothing can catch, the originals sit in an on-disk journal (under `MUTATION_ARM_STATE_DIR`, else the per-user state dir) written before the first edit: the next mutation_arm start restores a file that still holds exactly the killed run's mutant (a `RESTORED` line on stderr), and leaves a file edited since the kill untouched: a run that would mutate it is refused (exit 2, nothing written) with a line naming the original's copy and that killed run's journal directory - compare, restore by hand, then delete that one directory. A file a still-running mutation_arm is mutating is refused the same way. A journal it cannot write is a refusal too (exit 2, nothing mutated): point `MUTATION_ARM_STATE_DIR` at a writable directory. Every arm also runs with bytecode writing OFF and purges the cached `.pyc` for each mutated source before and after, and REFUSES rather than run when one cannot be removed: a length-preserving mutation applied in the same second the file was last edited leaves a cache that the restored source does not invalidate, so a later run fails against bytecode no source file contains while grep and `inspect.getsource` agree the code is right, and a cache predating the mutation is served IN PLACE of it, which measured SURVIVED 6 of 6 while the mutant never ran. `--cmd "<command>"` runs a NON-pytest arm (`cargo test -p crate`, `make check`) split without a shell: exit 0 survived, a failure killed, a mutant that does not build (or a command that cannot run) INCONCLUSIVE. Leading `NAME=value` tokens (`--cmd "CARGO_TARGET_DIR=/x cargo test -p crate"`) are added to the inherited environment of the baseline and every arm, as a shell sets them for one command, and the program after them is looked up on the PATH they give; nothing in them is expanded, so `$HOME` stays literal. A restore writes the original bytes with a FRESH mtime, so an mtime-keyed build cache (cargo, make) rebuilds the restored source instead of reusing the mutant's binary. An arm whose runner cannot import a module names it and the `--with DEP` rerun. `--test` takes ONE node id and repeats (every one runs in the same arm), and so does each entry of a battery's `tests`: a value holding several space-separated paths, or a pytest option, is refused (exit 2) before anything is written, since pytest reads it as one path and fails `file or directory not found`; a pytest exit 4 (usage error) or 5 (nothing collected) is reported as that (exit 2, the arm never ran), never as a red baseline. `--log-dir` never overwrites: each arm's log is named after its index and label (the node ids for a single arm) with a `-2`, `-3` suffix when taken, and the text report prints the path

## `mutation_arm --revert`

running a test against the COMMITTED version of a file while your fix is still uncommitted - `git show HEAD:f > f`, run the test, put the fix back by hand. The putting-back is where work is lost: `git checkout --` restores from the index and drops the fix, and a copy-aside in a shared scratch dir can be restored by a parallel agent's stale copy, which then reports success. `--revert FILE REV` swaps FILE for its text at REV for one arm and restores your work tree from a copy taken first, with the same byte check, `.pyc` purge and timeout as a mutation. The report names REV's resolved sha, so "red against HEAD" still means something after HEAD moves. Refuses, writing nothing, when FILE is outside a git work tree, absent at REV, or already identical to it

## `fanout_crosscheck`

"did any agent of a per-target fan-out write into a SIBLING's target?" - one agent per repo, package or memory level, each reporting success, and you about to commit on those reports. A misdirected write names its own target in the report and a sibling's identifier in the file, so reading reports or `git diff` per target by eye misses it, and a whole-file `grep` for the names drowns in old changelog lines that legitimately cite a dependency. It reads only the lines each target GAINED (plus untracked files, which `git diff` never shows) and looks there for the OTHER targets' names in snake, kebab and spaced spellings; a declared `pyproject.toml` dependency is not a finding. A plain-file target (a gitignored CLAUDE.local.md) counts every line as gained. Zero lines examined is exit 2, never a clean pass

## `guard_replay`

shipping a PreToolUse hook or guard on the strength of its unit tests. They prove it fires on the hazard you thought of; they cannot tell you whether it is QUIET on ordinary work, nor whether the times it speaks are times worth speaking - and those are two different questions, both of which have been answered wrong here on shipped hooks. Replays every real call in your Claude Code transcript corpus through the guard's OWN function - Bash by default, or `--tool Write` / `--tool Edit` to price a guard on what gets WRITTEN rather than run (Edit contributes the REPLACEMENT text, since that is what is about to land) - or `--field file_path` to price a guard on WHERE a write lands rather than on its text, because a path guard replayed on content measures the wrong question while reporting a confident rate; a tool whose payload it cannot read REFUSES and names the ones it knows, because reporting an empty corpus blames your history for a question the tool could not ask - with the cwd each command actually ran under (a guard that resolves paths answers differently per session dir), and reports the FIRING RATE and the PRECISION separately: how much of ordinary work it would interrupt, and how many of those calls a gate really refused. `--sample` prints firings to read, because a percentage tells you volume and never whether the warnings are right - spread evenly across the corpus, because the walk is file by file and so a first-N sample is one PROJECT's habits wearing the whole run's clothes. A sample is for seeing what the firings LOOK like; it cannot establish a ratio among them. Reading 40 of 557 put a residual at ~10 percent where all 557 put it at ~2, and the 517 unread held the shapes that mattered - so when a proportion is the answer you need, classify every firing. The corpus is the Claude Code transcript JSONL under `~/.claude/projects` (`--root` points elsewhere) - NOT shell history, which carries neither a cwd nor any record of what a gate did. Your predicate is called as `f(command)`, or with a second argument chosen by the parameter's NAME - `cwd` receives the call's directory and `tool_name` the tool being replayed, positional or keyword-only; any other name is left at its default - and anything truthy counts as a firing. It counts only where the guard FIRES, never where it should have fired and stayed silent: for its misses (recall) see the wider-oracle method under "Why a jig over a one-liner"

## `corpus_prompts`

pricing a rule that reads a PROMPT - a router trigger, a nudge, a classifier gate - by hand-walking `~/.claude/projects` for what people actually typed. `guard_replay` answers the same question for tool CALLS and cannot answer it here: a prompt has no gate, so its precision column means nothing, and the question becomes which prompts a rule speaks on. It diffs two predicates by their firing SETS rather than their counts, because two rules can fire the same number of times on different prompts, so a count diff of zero is exactly the shape that hides a narrowing that also admitted something new. Which records count is measured rather than assumed: most `type: user` records are the assistant's own tool traffic wearing the user role, `entrypoint` separates a person at a terminal from a headless SDK node, and `origin` is too rare on real transcripts to filter on. Your predicate is called as `f(text)` - the prompt TEXT alone, no record and no second argument, unlike guard_replay's `f(command, cwd)`, because a prompt has no cwd that changes its meaning. The prompts come back RAW: whether one is a slash command or an envelope is the caller's rule, and a second copy of that judgement here would drift from the one the hooks use

## `mdwrap`

re-flowing ONE paragraph of a long markdown file (TODO, design note, CLAUDE.md) to a column width by hand, and rewrapping the neighbours by accident - it takes an ANCHOR rather than a line-length rule, refuses an anchor that is missing or matches two paragraphs, and a paragraph that is a list, a heading, a blockquote, inside a code fence or holds a hard line break, and any wrap that would leave a line Markdown reads as a new block (a `---`/`===` underline, a thematic break, a fence, an HTML tag), keeps the file's line endings, and reports the changed line range. A one-item `* `/`+ `/`1. ` list counts as a list, and no wrapped line ends in a backslash (a hard break). Writes atomically, or in place for a hard-linked file or a directory that refuses the temp file (JSON `write`). Dry-run unless `--apply` (exit 2 = refused or error; there is no 1)

## `renamescope`

`sed -i 's/old/new/g'` across a file without knowing WHICH functions the hits land in - you give it the functions you SET OUT to change and it reports the hits that fall outside them, which is the finding, because there the substitution does not break, it changes meaning. It REPORTS only; the rename stays yours to run

## `plan_codecheck`

handing off a written PLAN whose code nobody has run, or hand-writing a one-off driver that pulls its python fenced blocks out and runs pytest, pyright and ruff on them - each such driver carries the last one's quirks: ruff fed on stdin with no filename reports import-order findings that do not exist at the real path, and pyright handed a path list analyses nothing when the project config excludes it. It places each block at the repo path it names (a `.py` path in the fence's info string, a first line `# file: path`, or the last backticked `.py` path just above the fence), copies the repository to a temporary directory, writes the blocks over the copy, and runs pytest (only when a test file is placed; collecting nothing is a failure), pyright strict on exactly the placed files (it must report analysing every one) and `ruff check --stdin-filename <repo path>` from the real root. A block is checked as the whole new content of its file. The real tree is never touched; a block with no path is named UNPLACED and keeps the run from passing

## `instrument_share`

re-measuring how much of real session time goes to the INSTRUMENTATION - memory upkeep, handovers, detours into the plugin's own source - by rebuilding a classifier over `~/.claude/projects` by hand, which makes two periods incomparable because the classifier changed between them. Classifies every tool call as work / memory / handover / skills-detour by its tool and input (running a shipped jig or reading a skill is work), charges each call the time to the next event capped at `--max-gap` minutes, groups consecutive instrumentation calls into EPISODES blamed on the Stop-hook block, SessionStart context or typed prompt before them, and reports minutes and share per ISO week and per trigger. Main session transcripts only (a subagent runs beside its parent, so counting it would double the clock); a call copied into a resumed transcript counts once; the plugin's own repository is skipped by default (`--exclude-cwd`). The figures are only as good as its patterns, so compare periods measured by one version

## `statusrot`

a memory entry still saying "shipped" / "deployed" / "TODO, not started" / "tracked as #34" long after that stopped being true - it sweeps the fact store for status claims and reports each as a CANDIDATE needing confirmation, never a verdict (ships in `meta-dream-tree`, not here)

## `factedit`

rewording a memory fact's always-loaded hook or replacing its body by hand - which level owns the slug, is the new hook under the cap, and does it still parse (ships in `meta-dream-tree`, not here)
