# Modern Python library choices

Default to current, well-maintained libraries over dated stdlib or legacy packages when the
better option is clear. Install third-party deps via `uv` (a tool with `uvx`, or a script with
PEP-723 inline metadata run by `uv run`). Libraries on this list are pre-approved: just use
them and let `uv` fetch them, no need to ask. These are general public defaults, not absolutes:
a project's own conventions win.

## Adding an entry

Before adding a library here, vet it: trustworthy (reputable maintainer or community, not a
typo-squat), common (widely adopted), and modern (actively maintained, current releases). Each
new row must carry: a short **description** of what it is for (in the `Use` cell), the older
library/libraries it **replaces** (in the `Avoid` cell), and - **whenever the pick is not
self-evident** - **why** it is better (the parenthetical note in the `Use` cell). A swap that
explains itself (`pathlib.Path` over `os.path`, `pytest` over `unittest`) needs no parenthetical;
a contested or trade-off pick (`isal` vs `deflate`, one MySQL driver over another) always does.
Keep rows one line; do not add anyone's private or in-house packages here.

If the new library overlaps in function with an existing entry, resolve it - never leave two
rows silently competing for the same job:
- **Both have a place:** keep both and make the distinction explicit - state when to use which
  and why (e.g. one streaming vs one one-shot, sync vs async, simple vs full-featured).
- **The new one supersedes the old:** only when you are sure, replace the old row with the new
  one, move the now-obsolete library into the new row's `Avoid` cell, and say why it was
  replaced.

## Structured data: pydantic at the edges, dataclasses inside

For any structured data in a Python app, parse untrusted/external input into `pydantic` models at
every boundary, and use `dataclasses` for pure internal layers. Do NOT use `attrs`, hand-woven
classes, or raw `dict`s for structured data. For the full end-to-end discipline (parse once at the
boundary, typed models throughout, Enums for fixed values, minimal conversions), use the
`bitranox:coding-python-data-architecture` skill.

## HTTP example (httpx2)

    import httpx2 as httpx          # API-compatible with httpx
    with httpx.Client(timeout=30.0, proxy="http://user:pass@host:port") as client:
        r = client.get("https://api.example.com/data")
        r.raise_for_status()
        data = r.json()

Use a `Client` for many requests (connection reuse), and `AsyncClient` under asyncio. Both
support `proxy=` (one proxy), `mounts=` (per-scheme proxy transports), `timeout=`, and HTTP/2.
There is no `proxies=` kwarg - httpx dropped it in 0.28 and httpx2 never had it, so passing it
raises `TypeError: Client.__init__() got an unexpected keyword argument 'proxies'`.

`httpx2` (`github.com/pydantic/httpx2`) is the legitimate Pydantic-org-stewarded successor to httpx
and a drop-in replacement. Some security scanners flag it as a typosquat - that is a FALSE POSITIVE
(verified: Pydantic org + Trusted Publisher + Sigstore). If a scanner re-flags it, re-verify the
publisher independently and surface it to the user rather than auto-dismissing; do not silently
swap it out.

## Notes

- **Reading a large JSON array one element at a time without a new dependency** (the table row
  above): open the file in binary mode and read chunks through
  `codecs.getincrementaldecoder("utf-8")()` into a `str` buffer, so a character split across two
  chunks still decodes; pass `final=True` on the read that hits end of file, or a file cut inside a
  character ends without an error. `raw_decode` skips neither leading whitespace nor the array's
  `[`, `,` and `]`, so step over those yourself (JSON whitespace is space, tab, LF and CR only, not
  `str.isspace()`) and refuse anything else there. At each element call
  `json.JSONDecoder().raw_decode(buf, i)` for its `end`: a `JSONDecodeError` before end of file
  means the element is not complete yet (read more, doubling the read size, and retry), at end of
  file it is a real error; an element ending exactly at the buffer's end before end of file may be a
  cut number, so read more first. A MALFORMED element raises the same `JSONDecodeError`, so without
  a limit the reader keeps reading to the end of the file before it refuses: set a maximum element
  size (a setting, counted in characters) and refuse once `len(buf) - i` exceeds it while the
  element is still incomplete. Deep nesting raises `RecursionError`, not `JSONDecodeError`: catch
  it and refuse with its own message (it is not malformed input). Where it starts depends on the
  interpreter. From Python 3.12 on, 5000 levels still parse (100000 do not), so up to orjson's own
  limit the records match: 1024 pass, and orjson refuses 1025 in `orjson.loads`. On 3.10 and 3.11
  `raw_decode` follows the recursion limit and stops at 997 levels at the default limit of 1000,
  so an element nested 998-1024 deep is refused there although orjson takes it. That 997 counts
  from a shallow stack, and every frame above the call takes one level (995 measured through a
  CLI's reader), so pin the depth you promise through the production call path, in a test that
  runs on every supported minor. Invalid UTF-8 raises
  `UnicodeDecodeError` from the decoder: map it to the same refusal. Then yield
  `orjson.loads(buf[i:end])` and advance `i`; drop the consumed prefix only when reading the next
  chunk (`buf = buf[i:] + new`), never per element, which would copy the buffer once per record. A
  value `raw_decode` accepts but orjson refuses (`NaN`, `Infinity`, a lone surrogate) raises from
  `orjson.loads`, as a whole-document orjson parse would. Peak memory is the buffer, bounded by the
  maximum element size, whatever the record count; prove it with peak RSS at two file sizes, plus
  one file whose FIRST element is malformed. Holding the whole file as one `str` instead grows with
  the file. Each element is parsed twice (stdlib, then orjson): that buys orjson's exact records,
  not speed.

- Prefer a library over an external command-line tool: `httpx2` instead of shelling out to
  `curl`, stdlib/`orjson` instead of `jq`, `re`/stdlib instead of `grep`/`sed`. Libraries are
  the same on every OS; external commands may be missing or take different flags on Windows.
- Reach for stdlib when no third-party library is warranted (small glue, no hot path): the
  point is "best tool", not "most dependencies".
- Logging and CLI framework are deliberately left to each project's own conventions rather
  than prescribed here.
- **When a project uses click, declare an OUTPUT path as
  `click.Path(..., writable=True, readable=False)`** (the same under `rich-click`). `readable`
  defaults to `True`, and for a target that already exists click runs `os.access(path, os.R_OK)`
  and exits 2 with `Path '...' is not readable.` (`File '...'` when `dir_okay=False`), so a target
  the user may write but not read is refused. macOS answers that check for `/dev/stdout` from the
  descriptor's open mode, so `-o /dev/stdout` with stdout on a pipe is refused there (observed in
  macOS CI) while Linux passes, and a Linux-only test never sees it. Pin it with a test that runs
  on every POSIX cell: create the target, `chmod` it to `0o200`, invoke the command with `-o` on it
  and assert exit 0; skip as root (root passes the check) and on Windows (`chmod` cannot make a file
  write-only there). Before a release note says a command works on a platform, confirm the command
  runs there at all.
- **`subprocess` raises a DIFFERENT exception type per OS for the same condition, so never branch
  on which one you got.** A missing `cwd` raises `FileNotFoundError` on POSIX but
  `OSError [WinError 267] "The directory name is invalid"` on Windows, so a
  `FileNotFoundError -> 127 / OSError -> 126` mapping returns two different exit codes for one
  condition - and the POSIX run stays green because POSIX happens to raise the type the code
  expected. Pre-check the path yourself (`Path(cwd).exists()` / `.is_dir()`) and decide the result
  explicitly, then run the missing-path test on Windows before trusting its exit code. Pick the
  pre-check by the code you want for a `cwd` that exists but is a FILE: after `exists()` it still
  reaches `subprocess` and raises `NotADirectoryError` (the 126 path), while `is_dir()` sends it to
  the missing-directory result.
- **On 3.14+, `except A, B:` without parentheses is VALID (PEP 758) and catches both** (so does
  `except* A, B:`). On 3.13 and earlier the same line is a `SyntaxError` under the old Python-2
  `except E, name:` grammar, so it reads like an obvious bug. Check `requires-python` or the
  interpreter and probe with `python -c` before "fixing" it; on 3.14+ adding parentheses is a style
  choice, not a correction.
- **Before importing a stdlib name added after the project's floor, read its own `requires-python`
  in `pyproject.toml`.** `tomllib`, `enum.StrEnum` and `ExceptionGroup` (with `except*`) arrived
  in 3.11 and `typing.override` in 3.12. Such an import passes every local gate on a newer
  interpreter and fails only in the oldest CI cell, often as unrelated-looking pyright-strict
  "partially unknown" errors. Take the version from the docs' "Added in version", not from memory.
  New projects start at `>=3.11`; an existing project's declared floor binds its CI. A name missing
  from an existing module raises plain `ImportError`, not `ModuleNotFoundError` (`from typing import
  override` on 3.11, `from enum import StrEnum` on 3.10), so guard with `except ImportError`, or use
  `typing_extensions.override`; `ExceptionGroup` is a builtin and needs the `exceptiongroup`
  backport; `except*` is syntax no guard can catch, so it means raising the floor. For TOML the
  floor is moot: `tomllib` is read-only and `tomli_w` is third-party, so `rtoml` stays the choice.
  The same floor reaches code you did not write for the project: a test that EXECUTES a CI
  workflow's inline script (extracts a step's `run:` block and runs it with `sys.executable`) runs
  it on the TEST interpreter, the oldest matrix cell included, while CI runs that step on whatever
  its `setup-python` names (often `3.x`). A script importing `tomllib` passes locally and fails
  every 3.10 cell with `ModuleNotFoundError`. Mark such a test
  `pytest.mark.skipif(sys.version_info < (3, 11), reason=...)` with the reason naming the step's
  interpreter, or run the script on an interpreter matching that `setup-python`.
- **Prefixing a docstring with `r` to satisfy ruff D301 changes EVERY escape in it at once.** Written
  non-raw, `\\` is one backslash and `\t`, `\n`, `\u2713` are real escapes; after `r"""` each is
  literal, and only some of the damage is loud. A doctest written for the non-raw form fails
  (`count("a\\tb")` now passes a backslash and a `t`, not a tab). Prose changes silently:
  `%APPDATA%\\vendor` renders with two backslashes, `\u2713` as six characters instead of a check
  mark. And an example can stay green on an input nobody meant: `"a\\nb".split("\\n")` still gives
  `['a', 'b']`, now splitting on a literal backslash-n. So after any conversion, rewrite each escape
  into its raw spelling - halve every `\\`, put the character itself in place of a `\u`/`\N{}`/`\x`
  escape (or reword, where the project bans non-ASCII source). Then prove nothing moved: the
  function's `__doc__` imported from the old source and from the new must be EQUAL, apart from any
  deliberate rewording - a mechanical check that catches all three kinds of damage and scales to
  a sweep of many hits - and run the doctests. Escaping only the offending backslash (`\d` to
  `\\d`) silences Python's invalid-escape warning but NOT D301, which fires on any backslash
  except a `\u`/`\N{}` escape or a line continuation (so a docstring whose only backslashes are
  those needs no `r` at all). ruff offers the `r` prefix only as an UNSAFE fix; never bulk-apply it
  with `--unsafe-fixes`.
- **Pass a computed `re.sub` replacement as a function, not a string.** `re` parses a string
  replacement as a template, so a backslash in dynamic text (file content, a Windows path,
  regex-like prose) raises `re.error` 'bad escape' (`re.PatternError` is its name on 3.13+), or
  silently turns `\1` / `\g<0>` into group references. Write `re.sub(rx, lambda m: text, s)`
  (`Pattern.sub` the same); a literal replacement is fine as a string. Do not run the data through
  `re.escape` to make it a safe template: that escapes punctuation and spaces, which the
  replacement then keeps as stray backslashes. If it must stay a string, double only the
  backslashes (`text.replace("\\", "\\\\")`). A batch loop over many files doing this should be
  idempotent, so a mid-loop crash can simply be re-run.
